# Requirements Document

## Introduction

This update rebrands the desktop POS and inventory management application from "DIRMS StoreBox PRO" to "Joainas Mart", removes the offline license activation system, introduces a depleted-stock sales workflow with a popup for inventory-authorized users, refines the price display logic for single-minimum or single-maximum pricing, and fixes a backup-recovery bug that corrupts inventory stock counts when more than five backup JSON files accumulate. The update must preserve all existing data across upgrades from any prior version (v1.x, v2.0.x) and ship as a new version.

## Glossary

- **Joainas_Mart**: The new brand name for the application, replacing "DIRMS StoreBox PRO". Used in app titles, window titles, edition config, metadata, receipts, financial records, and all user-facing text.
- **DroneBug_Technologies**: The software developer company. Retains a small credit line on receipts and financial statements. Not the primary brand.
- **Activation_Gate**: The current `ActivationGate` component that blocks app entry until a `.lic` file is imported and a password verified. To be removed in this update.
- **License_System**: The full offline licensing subsystem comprising `ActivationGate.tsx`, `license.ts`, and `license.rs` (Rust backend), including Ed25519 signature verification, Argon2id password checking, and `.lic` file activation.
- **POS_Module**: The `POSModule.tsx` component where point-of-sale operations occur, including barcode scanning, cart management, and checkout.
- **Inventory_Module**: The `InventoryModule.tsx` component for managing product catalog, stock levels, and pricing.
- **Edition_Config**: The `src/config/edition.ts` file defining `appName`, `shortName`, `version`, and other metadata.
- **Tauri_Config**: The `src-tauri/tauri.conf.json` file defining `productName`, window title, bundle metadata, and icons.
- **Product**: An inventory item with `retailPrice` (max price), optional `minPrice` (floor price), `priceTiers`, `stockQty`, and `kind` (product, service, or edible).
- **Stock_Qty**: The integer quantity of a product on hand. May go negative under the depleted-stock sell feature.
- **Depleted_Stock**: A product whose `stockQty` is less than or equal to zero and whose `kind` is not service or edible (i.e., `isUncountedKind` returns false).
- **Negative_Stock**: A stock state where `stockQty` falls below zero (-1, -2, ...-n) to record sales of borrowed or credit-supplied goods. When new stock is added, the count resets from negative to the positive added amount.
- **Inventory_Access**: A user capability set containing `'inventory'` and/or `'admin'`. Users with this capability can add stock or sell at negative stock when encountering depleted stock.
- **Price_Display**: The formatted representation of a product's price, shown in inventory lists, POS grids, receipts, and financial records.
- **Min_Price**: The optional floor price (`minPrice` field) below which a product cannot be sold. When set alone (without `retailPrice`), indicates the product can be sold at any price at or above this minimum.
- **Max_Price**: The `retailPrice` field, representing the ceiling price. When set alone (without `minPrice`), the product is sold at exactly this price.
- **Backup_Recovery**: The `tryRecoverFromJsonBackup()` function and related `adoptBackupPayload()` that scan the DB folder for `*backup*.json` files and merge recovered data into the live database.
- **Backup_Payload**: A JSON object containing `products`, `customers`, and `sales` arrays, validated by `isValidBackupPayload()`.
- **Receipt_Footer**: The mandatory text printed at the bottom of every receipt. Currently credits DroneBug Technologies; will retain a small developer credit line.
- **Financial_Records**: Receipts, financial statements, and audit logs generated by the application.

## Requirements

### Requirement 1: Rebrand Application to Joainas Mart

**User Story:** As a business owner, I want the application to display "Joainas Mart" as the brand name everywhere, so that my customers and staff see my store identity consistently.

#### Acceptance Criteria

1. THE Edition_Config SHALL set `appName` to "Joainas Mart Inventory Management System", `shortName` to "Joainas Mart", and `version` to "2.0.5".
2. THE Tauri_Config SHALL set `productName` to "Joainas Mart", the window title to "Joainas Mart - Inventory Management System", and `shortDescription` to reference "Joainas Mart".
3. WHEN the application loads, THE boot splash screen SHALL display "Joainas Mart" as the title text and use the Joainas Mart logo from the assets folder.
4. THE index.html page title SHALL be "Joainas Mart — Inventory Management System".
5. THE metadata.json `name` field SHALL be "Joainas Mart".
6. THE package.json `name` and `version` fields SHALL reflect "joainas-mart" and "2.0.5" respectively.
7. THE desktop shell sidebar, header logo, login modal, developer modal, and all component alt-text SHALL display "Joainas Mart" instead of "DIRMS StoreBox PRO" or "DIRMS".
8. WHEN the Joainas Mart logo is referenced, THE application SHALL use the logo from the assets folder as the default app icon, header logo, and receipt logo (replacing `/logo.png`).

### Requirement 2: Remove License Activation System

**User Story:** As a store owner, I want the application to start directly without any license activation step, so that I can use the app immediately after installation or update.

#### Acceptance Criteria

1. WHEN the application starts in Tauri runtime, THE App SHALL bypass the Activation_Gate and proceed directly to setup or login without checking License_System status.
2. THE App SHALL remove the `ActivationGate` component rendering from the startup flow.
3. THE build SHALL completely remove license-related Tauri commands (`get_license_status`, `import_license`, `activate_license`, `deactivate_license`) from the Rust backend invoke handlers.
4. WHEN a user opens the developer info modal, THE developer modal SHALL not display license status fields.
5. THE initial printer config and developer info in `initialData.ts` SHALL be rebranded to "Joainas Mart" without referencing the license edition label.

### Requirement 3: Update Compatibility and Data Preservation

**User Story:** As a store owner upgrading from an older version, I want my existing products, sales, customers, users, and settings to be preserved, so that I do not lose business data on update.

#### Acceptance Criteria

1. WHEN the application updates from any prior version (v1.x or v2.0.x), THE Storage layer SHALL preserve all existing products, sales, customers, users, categories, and settings.
2. THE `hasInstallEvidence()` function SHALL continue to detect prior installations so the setup wizard never reappears on an update.
3. THE `tryMergeSiblingDatabases()` function SHALL continue to merge legacy database files from prior app identifiers.
4. WHEN legacy data keys are encountered, THE Storage layer SHALL migrate them to the current schema without data loss.
5. THE identifier in Tauri_Config SHALL remain "com.dronebug.dirms.desktop" to preserve the app data directory across updates.

### Requirement 4: Depleted Stock Sales Popup for Inventory-Authorized Users

**User Story:** As an admin or inventory-authorized user, I want a popup when I try to sell a depleted stock item that lets me either add stock or sell at negative stock, so that I can maintain sales records even when stock is borrowed or credit-supplied.

#### Acceptance Criteria

1. WHEN a user with Inventory_Access attempts to add a Depleted_Stock item to the cart in the POS_Module, THE POS_Module SHALL display a popup modal instead of blocking the sale.
2. THE popup modal SHALL display the message "X is run out. Would you add if you have it available?" where X is the product name.
3. THE popup modal SHALL contain an integer input field with a placeholder example value and a Save button that, when submitted, updates the product's Stock_Qty directly in the Inventory_Module and then adds the item to the cart.
4. THE popup modal SHALL also offer a "Sell at negative stock" option that, when selected, allows the sale to proceed and decrements the product's Stock_Qty into negative values (-1, -2, ...-n).
5. WHEN the "Sell at negative stock" option is used and subsequent stock is later added to that product, THE Inventory_Module SHALL reset the Stock_Qty from its negative value to the positive added amount (e.g., if Stock_Qty is -3 and 5 units are added, Stock_Qty becomes 5, not 2).
6. WHEN a user with Inventory_Access selects neither option and closes the popup, THE POS_Module SHALL not add the item to the cart.
7. THE popup modal SHALL present both the "add stock" input and the "sell at negative stock" option in a single popup, not as separate sequential dialogs.

### Requirement 5: Depleted Stock Notification for Non-Inventory Users

**User Story:** As a cashier without inventory access, I want to be informed when a product is depleted so that I can notify the admin, but I should not be able to sell depleted items.

#### Acceptance Criteria

1. WHEN a user without Inventory_Access attempts to add a Depleted_Stock item to the cart in the POS_Module, THE POS_Module SHALL display a simple, easy-to-understand message informing the user to notify the admin about the depleted stock.
2. THE message SHALL not contain an input field or a sell option for users without Inventory_Access.
3. THE POS_Module SHALL not add the Depleted_Stock item to the cart for users without Inventory_Access.
4. THE notification message SHALL reference the product name in the depleted stock notification, and this requirement SHALL apply to any depleted-stock notification message regardless of the viewer's Inventory_Access level.

### Requirement 6: Price Display Logic for Single and Dual Pricing

**User Story:** As a store owner, I want prices displayed according to which price fields I set, so that the display accurately reflects my pricing strategy without confusing range formatting.

#### Acceptance Criteria

1. WHEN a Product has only Max_Price set (retailPrice > 0, minPrice not set or 0), THE Price_Display SHALL show only the max price as "₦X" without range formatting or a "(min)" suffix.
2. WHEN a Product has only Min_Price set (minPrice > 0, retailPrice not set or 0), THE Price_Display SHALL show the min price with a "+" sign as "₦X+" to indicate the product cannot be sold below the minimum but can be sold at any higher price.
3. WHEN a Product has both Min_Price and Max_Price set (both > 0 and not equal), THE Price_Display SHALL show the range "₦min – ₦max".
4. THE Price_Display logic SHALL apply consistently across the Inventory_Module list view, the POS_Module product grid and search results, receipts, and financial records.
5. THE `formatRange()` function in pricing.ts SHALL produce the output specified in criteria 1, 2, and 3.
6. THE `renderPriceRange()` function in InventoryModule.tsx SHALL produce the output specified in criteria 1, 2, and 3.

### Requirement 7: Fix Backup Recovery Inventory Corruption Bug

**User Story:** As a store owner, I want my inventory stock counts to remain accurate even when many backup JSON files accumulate, so that I do not see wrong, low, minimized, or excessive stock levels.

#### Acceptance Criteria

1. WHEN more than 5 backup JSON files exist in the database folder, THE Backup_Recovery function SHALL not corrupt or duplicate inventory Stock_Qty values.
2. THE `adoptBackupPayload()` function SHALL never overwrite existing live product Stock_Qty values with backup values when the product already exists in the live cache.
3. WHEN `adoptBackupPayload()` merges backup products, THE function SHALL only add products that do not already exist by ID in the live cache, and SHALL not modify the Stock_Qty of existing products.
4. THE Backup_Recovery function SHALL process backup files in a deterministic order (most recent first) and stop after the first valid file that yields recovered data, rather than merging data from multiple backup files in a single pass.
5. WHEN a backup file has already been processed (marker exists in app_settings), THE Backup_Recovery function SHALL skip that file.
6. THE `isValidBackupPayload()` function SHALL validate that the `products` array entries contain numeric `stockQty` fields before adoption, and SHALL reject payloads with non-numeric or missing stock quantities.

### Requirement 8: Receipt and Financial Record Branding

**User Story:** As a business owner, I want receipts and financial records to show Joainas Mart branding with a small developer credit for DroneBug Technologies, so that my customers see my store name while the developer is still credited.

#### Acceptance Criteria

1. WHEN a receipt is printed, THE receipt header SHALL display "Joainas Mart" as the business name when no custom business name is configured.
2. THE receipt footer SHALL display the Joainas Mart thank-you note followed by a small developer credit line for DroneBug Technologies.
3. THE `MANDATORY_RECEIPT_FOOTER` constant SHALL retain the DroneBug Technologies credit text.
4. THE initial printer config in `initialData.ts` SHALL set `storeName`, `businessName`, `receiptHeaderNote`, and `address` defaults to "Joainas Mart".
5. WHEN a financial statement is generated, THE FinancialStatementPaper component SHALL default the business name to "Joainas Mart" when no custom name is configured.
6. THE financial statement developer verification section SHALL display "Joainas Mart" as the software name with DroneBug Technologies as the developer company.

### Requirement 9: New Version Marking

**User Story:** As a user, I want the application to clearly indicate it is a new updated version, so that I know I am running the latest release.

#### Acceptance Criteria

1. THE Edition_Config version SHALL be "2.0.5", representing a new feature release.
2. THE Tauri_Config version SHALL be "2.0.5".
3. THE package.json version SHALL be "2.0.5".
4. WHEN the developer info modal is opened, THE modal SHALL display version "2.0.5" with the "Joainas Mart" brand name.
5. THE short description in Tauri_Config SHALL reference "Joainas Mart v2.0.5".
